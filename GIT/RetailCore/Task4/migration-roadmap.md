#  Roadmap миграции
## Этапы перехода

### Этап 1. Подготовка, стадия аналитики
**Описание этапа:**
- Убрать неизвестность, которая мешает задать критерии миграции 
- Задокументировать все интеграции, зависимости, скрытые сценарии
- Создать, согласовать карту потоков данных
- Создать, согласовать модель данных
- Создать тестовые сценарии и тестовые данные для регресса
- Подготовить инфраструктуру для развертывания брокера сообщений
- Настроить мониторинг и алертинг

**Риски:**
- Неполные или неактуальные контракты; отсутствие базовой линии
- Отсутствие актуальных и достоверных сведений для построения полной картины устройства системы
- Проблемы при развертывании инфраструктуры - неподдерживается софт, несовместимость версий, отсутствие экспертизы у команды и т.п.

**Критерии завершения:**
- Выполнены все шаги из описания этапа

### Этап 2. Внедрение событийного слоя и аналитики
**Описание этапа:**
- Внедрение Transactional Outbox в монолите
- Настройка Kafka, создание топиков, запись в топик и чтение из топика.
- Изменение архитектуры: таблица исходящих событий, издатель, брокер, схема события  

**Риски:**  
- Потеря событий при сбое Transactional Outbox  

**Критерии завершения:**
- Outbox работает в ПРОДе, события публикуются для всех новых заказов.
- Read replica Oracle используется для менее половины аналитических запросов.

### Этап 3. История и статусы
**Описание этапа:**
- Перевести первый read-only сценарий из монолита
- Создать сервис истории, модель чтения, API и управляемую маршрутизацию
- Предоставить единый внешний статус, историю и время обновления
- Изменение архитектуры: сервис истории, модель чтения, API и управляемая маршрутизация  

**Риски:**
-Неизвестный статус, потеря наблюдаемости или превышение согласованных порогов

**Критерии завершения:**
- Поток событий стабилен и сверяется с Oracle

### Этап 4. Аналитическая витрина
**Описание этапа:**
- Перевести основные отчёты с Oracle на событийную витрину. Старые отчёты продолжают работать параллельно до окончания тестирования и переключения

**Риски:**
- Разная трактовка скидки, статуса или факта доставки
- Изменение методологий расчета в процессе работ этапа

**Критерии завершения:**
- Владелец показателя принимает формулу и результат сверки
- Новый отчёт принят и не читает операционную Oracle

### Этап 5. Интеграционный слой. Адаптер для первого партнёра
**Описание этапа:**
- Создать единый интеграционный слой (шлюз), ликвидировать обмен через staging-таблицы Oracle
- Миграция интеграций доставки на Gateway; 
- Замена staging таблиц на события Event Stream; 
- Миграция .NET сервиса на событийную модель; 
- Отключение старых интеграционных путей - адаптер для первого партнёра

**Риски:**
- Изменение формата у партнёра в процессе работ этапа
- Дубли заявок; рассинхронизация статусов у партнёров, неполадки на стороне партнёров

**Критерии завершения:**
- Контракт и статусы партнёра описаны
- Партнёр работает через адаптер, старый маршрут сохранен и существует как резервный

### Этап 6. Данные, архив и изоляция промо
**Описание этапа:**
- Снижение зависимости от Oracle и подготовка дальнейшего выделения логики
- Новые витрины, архив, единый контракт промо и теневой расчёт 

**Риски:**
- Потеря истории и неверная цена
- Изменение сумм действующих акций

**Критерии завершения:**
- Перенесённые данные восстанавливаются; выбранные промо-правила дают подтверждённый результат
- Расхождение скидки между путями измерено и принято


### Промежуточные состояния

1. События публикуются и сверяются  
2. История и внешний статус читаются из новой модели  
3. Первый отчёт строится из витрины   
4. Один партнёр работает через адаптер   
5.  Выделенные чтение, аналитика и первый адаптер  

### Зависимости 
Все этапы выполняются последовательно.
Зависимости между этапами имеют последоватеьность:  
Этап 1 --> Этап 2 --> Этап 3 --> Этап 4 --> Этап 5 --> Этап 6
