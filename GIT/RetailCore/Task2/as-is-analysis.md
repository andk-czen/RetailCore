# Краткий анализ артефактов

## 1. PlantUML-диаграмма — одно из существующих представлений текущего состояния
Даёт базовое представление о компонентах системы: компоненты, внешние экторы, основные потоки данных

## 2. Фрагмент исходного кода - `OrderProcessingService.java`
Присутствует смешение ответственности: бизнес-правила заказа, расчёт промо, маршрутизация доставки, работа со статусами, синхронные обращения во внешние системы.
Существуют различные надбавки, значения которых указаны напрямую в коде без использования справочников и занесения в слой данных.
Присутствуют фрагменты sql кода и обращения к базе напрямую, без изоляции слоя данных.
Присутствует смешение ответственности в монолите: расчёт цены, промо, маршрутизация, статусы, прямые SQL, синхронные внешние вызовы.
Используются staging‑таблицы для интеграции с .NET‑сервисом.
Синхронные вызовы логистики и платежей в рамках транзакции оформления заказа.
Batch‑механизм повторных попыток (RETRY_DELIVERY_QUEUE).
При недоступности промо-сервиса используется резервный вызов процедуры Oracle, а обмен с .NET-сервисом организован через staging-таблицы.
Показывает высокую связность монолита и сложное выделение отдельных функций в самостоятельные компоненты.

## 3. Стенограмма интервью interview-business.md
Фиксирует бизнес-цели, приоритеты, допустимые риски, критерии успеха, ограничения
Бизнес ожидает промежуточную ценность на каждом этапе и не готов к полной остановке.
Бизнес рассчитывает на поэтапную трансформацию без остановки текущих операций. 
Каждый этап должен давать понятный промежуточный результат, а не откладывать всю ценность до завершения программы.

## 4. Стенограмма интервью interview-support.md 
Фиксирует проблемы стейкхолдеров команды поддержки - непрозрачность, ручные операции, расхождение статусов, зависимость от команд
Поддержка компенсирует недостатки системы ручными действиями и накопленным опытом сотрудников.
Разбор нестандартных заказов требует обращения к нескольким инструментам и взаимодействия со смежными командами.
Для клиента критична прозрачность и предсказуемость; расхождения статусов — главный источник обращений.

## 5. Стенограмма интервью interview-1-tech-lead.md
Предоставляет понимание о техническом устройстве монолита, проблемах связности, Oracle-зависимостях 
Подтверждает, что монолит — центральный оркестратор с высокой связностью.
Выявлена фрагментированная логика промо (код + Oracle + внешние сервисы + fallback).
Статусы распределены между сервисами, batch и ручными инструментами.
Oracle используется не только как хранилище, но и как шина (staging‑таблицы) и как место хранения бизнес‑логики (процедуры).
Наблюдаемость ограничена: корреляционные ID не везде, восстановление цепочки — ручная работа.

## 6. Стенограмма интервью interview-2-logistics.md
Даёт понимание об отличиях интеграций, проблемах идемпотентности
Нет единого интеграционного контура: смесь REST, очередей, таблиц, batch.
Правила маршрутизации доставки распределены по слоям (код, конфиги, Oracle).
Критичны ручные исключения и ночные правки.
Проблемы с дедупликацией и повторной обработкой; семантика доставки сообщений несогласована.
Подчёркивается опасность недооценки исключений при проектировании.

## 7. Стенограмма интервью interview-3-analytics.md
Описывает проблемы аналитического контура - отсутствие канонической модели, нагрузка на Oracle, конфликты данных 
Отсутствие канонической модели заказа: разные интерпретации в витринах.
Аналитика напрямую зависит от Oracle, тяжёлые SQL влияют на операционную базу.
Слабая прослеживаемость lineage; часть происхождения полей — «через людей».
Проблемы аналитики отражают архитектурные дефекты операционного контура.
