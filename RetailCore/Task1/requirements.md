# Список ключевых функциональных требований
Система должна поддерживать ролевую модель с возможностью предоставления функций по ролям: Клиент, Оператор поддержки, Бизнес-пользователь, - Оператор службы доставки
- Система должна предоставлять возможность Клиенту выбрать товар
- Система должна предоставлять возможность Клиенту расчитать стоимость заказа
- Система должна предоставлять возможность Клиенту скидки и акции
- Клиент должен иметь возможность оформить заказ
- Клиент должен иметь возможность выбрать доставку при оформлении заказа
- Клиент должен иметь возможность выбрать форму оплаты
- Клиент должен иметь возможность оплатить заказ онлайн
- Клиент должен иметь возможность проверить статус оформленного заказа
- Клиент должен иметь возможность отменить оформленный заказ
- Клиент должен иметь возможность оформить возврат ранее приобретенного товара
- Бизнес-пользователь должен иметь возможность просматривать управленческие отчеты
- Оператор поддержки должен иметь возможность изменить статус заказа
- Оператор поддержки должен иметь возможность просмотреть технические атрибуты заказа
- Оператор поддержки должен иметь возможность перевести обращение в определенный сценарий обработки
- Оператор поддержки должен иметь возможность поставить служебный комментарий
- Оператор поддержки должен иметь возможность отправить заказ на повторную проверку
- Оператор поддержки должен иметь возможность поставить флаг для ручного разбора
- Оператор поддержки должен иметь возможность поменять технический статус
- Оператор поддержки должен иметь возможность выполнить ручной разбор
- Оператор поддержки должен иметь возможность проверить данные заказа
- Оператор поддержки должен иметь возможность зарезервировать товар
- Оператор службы доставки должен иметь возможность просмотреть список полученных заказов
- Оператор службы доставки должен иметь возможность просмотреть атрибуты заказа (адрес, контакты, статус)


# Список архитектурно значимых нефункциональных требований
- Система должна поддерживать работу со следующими каналами продаж: сайт, МП, маркетплейc.
- Работоспособность каждого из каналов продаж для системы является критичной.
- Контур оформления заказа (checkout), расчета стоимости и резервирования должен сохранять работоспособность при кратных пиковых нагрузках (сезонные распродажи, маркетинговые акции). Время отклика на этапе оформления заказа не должно деградировать при росте входящих запросов.
- Система должна предоставлять возможность проследить полный путь заказа от момента его создания до завершения по единому уникальному идентификатору.
- Необходимо снизить ТТМ и повысить гибкость системы, позволяющую внедрять новые функции и процессы
- Базовый процесс заказа должен стать стабильнее и предсказуемее (нужно указать точные критерии)
- Задержка или недоступность внешних сервисов (платёжные провайдеры, маркетплейсы, службы доставки) не должна блокировать базовый процесс оформления заказа
- Актуализация статуса заказа - необходимо избежать нарушения целостности данных из-за распределенных модулей и разных команд


## Требуют уточнения критерии оценки для:
- **Надёжность**: конкретные значения SLA/SLO (доступность, время отклика).
- **Катастрофоустойчивость**: RTO/RPO для критических сервисов.
- **Производительность**: показатели p95/p99 латенции и допустимые пороги.
- **Масштабируемость**: пропускная способность (RPS/TPS) в пиковые нагрузки.
- **Отказоустойчивость**: правила деградации при отказах внешних систем.
- **Консистентность**: требования к согласованности данных (strong vs eventual consistency).
- **Бизнес-метрики**: ожидаемый рост объёма заказов и пользователей.
- **Рамки проекта**: точный бюджет и сроки трансформации.


# Cписок ограничений и допущений
- Монолитное ядро на java
- Централизованная БД Oracle
- Cервисы на Python
- Сервисы на .net
- Разные типы взаимодействия (прямые вызовы, через БД, асинхронно)
- Десятки терабайт накопленной информации
- Архивирование реализовано частично
- Используемая БД ограничивает скорость и производительность
- Нельзя останавливать бизнес, работа системы должна быть непрерывной
- Поддержка партнерских сценариев для интеграций (приходится использовать нестандартные решения)
- Нельзя одномоментно перейти на новые интеграции
- Импортонезависимость не должна приводить к остановке процессов
- Оформление заказа, оплата, доставка - ключевые сервисы, в пиковые периоды создают повышенную нагрузку
- При изменениях необходимо использовать последовательные изменения небольшими итерациями с понятным ощутимым эффектом для бизнеса и постепенным поступлением инвестиций
